2. Цели и критерии успеха

Цель проекта

Создать веб-приложение для автоматизированного анализа данных газовых счётчиков, позволяющее диспетчерам быстро выявлять нештатные ситуации и отклонения от нормальных режимов работы.

Бизнес-боль заказчика

Организация пропускает Нештатные ситуации, после чего потребители требуют возмещения расходов. Система должна исключить человеческий фактор при выявлении таких ситуаций.

Критерии успеха (метрики)

≤ 1 мин

0%

Доля пропущенных критичных нештатных ситуаций

−50%

Снижение трудозатрат диспетчера на анализ данных

4. Функциональные требования

4.1. Загрузка данных

  • Ручная загрузка Excel: диспетчер загружает файл через веб-интерфейс.
  • Автоматическая загрузка (этап 2): система сама забирает данные по API или из БД.
  • Парсинг: извлечение ID счётчика, дата/время, расход, давление, температура, код НС.
  • Валидация: проверка корректности (расход не может быть отрицательным и т.п.).
  • Сохранение: запись в БД с привязкой к счётчику и времени.

4.2. Хранение данных

  • Справочник счётчиков: ID, адрес, собственник, пороговые значения (давление min/max, температура min/max, расход min/max).
  • История показаний: дата/время, расход, давление, температура.
  • Нештатные ситуации (НС): дата/время, код НС, описание, приоритет, статус (новая / обработана).
  • Пользователи: логин, пароль, роль (диспетчер / админ), список закреплённых объектов.
  • Логи: дата/время, пользователь, действие, IP-адрес.

4.3. Анализ и детекция (3 уровня)

Этап 1 — НС из кодов «Акцент»: получаем готовые коды нештатных ситуаций, отображаем на вкладке №1 с приоритетами.
Этап 2 — Сверка с порогами: сравниваем полученные данные с индивидуальными пороговыми значениями каждого объекта. Отклонения — на вкладку №2.
Этап 3 — Продвинутая аналитика: функция анализа данных за период. Резкие скачки, странные паттерны → на вкладку №3.

Признаки аварийных ситуаций

ПризнакОписаниеПриоритет
Расход = 0 Остановка счётчика — ключевая бизнес-боль Критично
Резкое изменение расхода Падение или рост в 2+ раза Высокий
Падение давления Например: было 0,4 Па → стало 0,2 Па Высокий
Выход за пороги Давление / температура / расход ниже min или выше max Средний
НС прибора Расход ниже нижнего или выше верхнего предела измерения Техническое

4.4. Веб-интерфейс

  • Дашборд диспетчера: список закреплённых объектов, фильтры (статус, адрес, собственник), сортировка (по приоритету, по времени последней НС).
  • Вкладка «Нештатные ситуации»: список всех НС с приоритетами (красный / жёлтый / зелёный), возможность отметить как обработанную с комментарием.
  • Вкладка «Отклонения от порогов»: объекты, где параметры вышли за пределы.
  • Страница детального просмотра объекта: графики расхода / давления / температуры за сутки / неделю / месяц, история показаний, история НС.
  • Страница загрузки Excel (для диспетчера).
  • Страница управления пользователями (для админа).
  • Страница просмотра логов (для админа).

4.5. Авторизация и роли

РольПрава
Диспетчер Видит только закреплённые объекты; может загружать Excel; отмечать НС как обработанные; просматривать графики и историю.
Админ (руководитель) Видит все объекты и всех диспетчеров; просматривает логи; видит необработанные НС (эскалация).

4.6. Уведомления и эскалация (этап 4)

  • Уведомления: новая НС высокого приоритета; критичная аномалия.
  • Эскалация: НС не обработана за N часов → повторное уведомление; за M часов → уведомление руководителю.

4.7. Логирование

  • Входы в систему: дата/время, пользователь, IP.
  • Действия: загрузка Excel, отметка НС, просмотр объекта, изменение настроек.
Логи входов — критическое требование MVP. Позволяют установить, кто и когда был ответственным за пропущенную НС.

7. Этапы и сроки

1–2 недели

Этап 0. Раскопки и интеграция

Получение документации от заказчика, примеров Excel, справочника кодов НС. Сбор пороговых значений по всем 400 объектам. Согласование формата данных.

3–4 недели

Этап 1. MVP

Загрузка Excel → парсинг → БД → веб. Два ЛК (админ / диспетчер). Логи входов. Вывод НС и отклонений от порогов.

2–3 недели

Этап 2. Автоматизация загрузки

Автоматический забор данных по API или через БД. Обработка ошибок и уведомления админу о сбоях.

3–4 недели

Этап 3. Продвинутая аналитика

Детекция аномалий по графикам (скачки, падения, нулевой расход). Визуализация с наложением порогов. Приоритизация.

2 недели

Этап 4. Уведомления и эскалация

Уведомления, эскалация на руководителя при игнорировании НС, журнал обработки.

2–3 недели

Этап 5. Пилот и доработки

Тестирование на группе из 50 объектов. Обучение диспетчеров. Сбор обратной связи. Внесение правок.

Постоянно

Этап 6. Промышленная эксплуатация

Подключение всех 400 объектов. Резервное копирование. Мониторинг доступности. Передача в эксплуатацию.

Итого до пилота: ~13–18 недель (3–4 месяца).

8. Риски и меры по их смягчению

Нет API

Только ручная загрузка Excel. Смягчение: на этапе 2 оставить ручную загрузку с напоминаниями диспетчеру.

Высокий

Высокий
Нет справочника кодов НС

Неправильная интерпретация нештатных ситуаций. Смягчение: получить документацию.

Средний
Пороговые значения не оцифрованы

Невозможна автоматическая сверка. Смягчение: собрать данные по всем 400 объектам на этапе 0.

Средний

НС остаются необработанными. Смягчение: эскалация на руководителя, логи действий, отчётность.

9. Открытые вопросы (требуют уточнения)

🔴 Блокеры — без ответов нельзя начинать

1. Есть ли у стороннего ПО готовое API для автоматической выгрузки данных? Если да — какое (REST / SOAP)? Есть ли документация?
2. Как выглядит структура Excel-файла? Нужен пример хотя бы одной строки (ID, дата/время, расход, давление, температура, код НС).
3. Какие коды нештатных ситуаций (НС) использует ПО? Есть ли справочник кодов?
4. Где сейчас хранятся пороговые значения (давление, температура, расход) для каждого из 400 объектов? В Excel? В стороннем ПО? В бумажном журнале?

🟡 Важные вопросы

  • 5. Как распределены объекты между диспетчерами? Каждый видит все 400 или у каждого своя группа?
  • 6. Что делать, если диспетчер пропустил НС? Руководитель видит все НС или только необработанные за N часов?
  • 7. Как диспетчер сейчас работает с НС (звонит / отправляет бригаду / фиксирует в журнале)? Нужно ли формировать заявки на выезд?
  • 8. Какие графики нужны (расход / давление / температура за сутки / неделю / месяц)? Нужно ли накладывать пороги на график?

Риски компактной команды:
  • Full-stack разработчик должен быть действительно сильным специалистом (уровень Senior). Найти такого сложнее, но возможно.
  • РП/СА в одном лице — двойная нагрузка. Риск: либо проект ведётся в ущерб аналитике, либо наоборот. Рекомендуется чётко распределять время (например, 60% аналитика / 40% управление).
  • Высокая зависимость от каждого — если один человек заболеет или уволится, проект встанет. Мера: документировать всё, держать знания распределённо.
  • Меньше параллелизма — задачи выполняются последовательно. Сроки могут увеличиться на 2-4 недели.
Компенсация рисков:
  1. Использовать готовые решения (Vuetify для UI, готовые шаблоны админок) — экономит 30-40% времени frontend
  2. Документацию вести в формате "living docs" (обновляется по ходу проекта), а не писать в конце
  3. Приёмку проводить поэтапно (после каждого этапа BRD), а не в конце всего проекта
  4. Для UX/UI использовать готовые дизайн-системы (Material Design) вместо кастомной разработки

10.8. Рекомендуемая структура финансирования

Оптимальная модель оплаты:
  1. 20% — аванс при старте проекта (этапы 0–1)
  2. 30% — после сдачи MVP (этап 1)
  3. 30% — после завершения пилота (этап 5)
  4. 20% — после промышленной приёмки

Такая структура защищает обе стороны: заказчик платит за результат, подрядчик получает оборотные средства.

Следующий шаг: Для уточнения бюджета нужно:
  1. Получить от заказчика информацию о существующих лицензиях (Windows, MS SQL)
  2. Узнать точную сумму возмещений потребителям за пропущенные НС (для ROI)
  3. Согласовать требования ИБ (влияют на стоимость инфраструктуры)
  4. Определить модель реализации: подрядчик / in-house / гибрид
